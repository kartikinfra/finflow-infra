# Falco Custom Rules for FinFlow

## Objective

Write production-grade Falco security rules for FinFlow's postgres container:
- Detect unexpected shell spawns inside postgres pod → CRITICAL
- Understand and debug rule loading, trigger pipeline, and kernel-level visibility

---

## What Was Built

### Rule: `postgres-shell-exec-detection`

```yaml
customRules:
  falco_rules.local.yaml: |-
    - macro: user_known_contact_k8s_api_server_activities
      condition: container.name contains "k8s_grafana-sc"
      override:
        condition: append
    - rule: postgres-shell-exec-detection
      desc: Detect shell execution inside postgres container
      condition: >
        spawned_process
        and shell_procs
        and container.image.repository contains "postgres"
      output: >
        Postgres container shell detected |
        process=%proc.name cmd=%proc.cmdline container=%container.name
      priority: CRITICAL
      tags: [postgres, security, k8s]
```

### Key Decisions

| Decision | Reason |
|---|---|
| `shell_procs` over `proc.name in ("bash", "sh")` | Covers all shells: ash, bash, zsh, dash, ksh, csh — attacker won't be limited to bash |
| `container.image.repository` over `container.name` | Container names are autogenerated and change on restart; image repository is stable |
| `spawned_process` macro | Built-in Falco macro mapping to `execve/execveat` syscalls — verified from default rules |

## Debugging Journey

### Problem 1 — `container.name` unreliable
**Discovery:** Falco's own default rules have a comment — *"container name is autogenerated, so there isn't"* — confirming it shouldn't be used for matching.  
**Fix:** Switched to `container.image.repository contains "postgres"` — verified against actual pod (`postgres:15-alpine`).

### Problem 2 — Rule not triggering
**Symptoms:** Rule loaded correctly in `/etc/falco/rules.d/falco_rules.local.yaml`, no parse errors, but zero alerts on `kubectl exec`.  
**Debug steps:**
1. Confirmed Falco was generating other alerts — not a dead Falco issue
2. Removed container filter entirely — still no trigger
3. Checked `shell_binaries` list — `bash`, `ash` both present
4. Verified `bash` and `ash` exist in `postgres:15-alpine` — both at `/bin/`

### Problem 3 — Root Cause: Rancher Desktop Architecture Limitation

Ran `bpftrace` inside Lima VM to trace `execve` directly:

```bash
rdctl shell
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s %s\n", comm, str(args->filename)); }'
```

**Finding:** Lima VM kernel's `execve` tracepoint is functional — k3s and host processes appear. But `kubectl exec` into a pod does **not** appear.

**Root cause:**
```
Mac Terminal → kubectl exec → k3s API Server (direct TCP tunnel)
                                      ↓
                              Container process spawned
                              (outside Lima VM kernel's tracepoint visibility)
```

`kubectl exec` bypasses the Lima VM kernel's syscall tracepoint path. Both Falco (modern BPF probe) and bpftrace miss these events — not because the rule is wrong, but because the execution path never crosses the monitored kernel surface.

Additionally, several older syscall tracepoints are missing on this kernel:
```
sys_enter_creat — No such file or directory
sys_enter_open  — No such file or directory
```

## eBPF Investigation — Validating Falco from the Kernel

When Falco stopped responding, the debug went deeper — directly into the kernel using `bpftrace` to independently verify what syscalls were actually visible.

### Script: `trace-execve-validation.bt`

```bpftrace
// Purpose: Validate execve syscall visibility in Lima VM kernel
// Used to cross-check why Falco's spawned_process rule was not triggering
// Run inside: rdctl shell (Rancher Desktop Lima VM)

tracepoint:syscalls:sys_enter_execve
{
    printf("%-16s %-6d %s\n", comm, pid, str(args->filename));
}
```

**Run:**
```bash
rdctl shell
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s %s\n", comm, str(args->filename)); }'
```

**Output observed:**
```
k3s-server  /usr/sbin/ip6tables
k3s-server  /var/lib/rancher/k3s/data/cni/flannel
lima-guestagent  /usr/sbin/iptables
```

### What This Proved

| Question | Answer |
|---|---|
| Is `execve` tracepoint alive in Lima kernel? |  Yes — k3s processes visible |
| Does `kubectl exec` into a pod trigger `execve`? |  No — never appeared |
| Is Falco broken? |  No — kernel itself doesn't expose the event |

### eBPF vs Falco — Same Kernel Surface

Both `bpftrace` and Falco's modern BPF probe attach to the **same kernel tracepoints**. If `bpftrace` can't see `kubectl exec` events, Falco can't either. This is not a Falco configuration issue — it's a fundamental visibility boundary.

**Key insight:** eBPF tools are only as powerful as the kernel surface they can attach to. On Rancher Desktop, `kubectl exec` traffic routes through a virtualization layer that places container processes outside the Lima VM's tracepoint visibility.

## Falco Key Learnings

- Always verify field names from actual Falco rules — `helm show values` and `cat /etc/falco/falco_rules.yaml` before writing conditions
- `spawned_process` is a macro, not a field — no `=` operator
- `in (list_name)` syntax for multi-value matching
- `override: condition: append` is the correct syntax for Falco 0.43.0+ macro overrides
- Falco uses syscall fields only — K8s audit fields like `ka_uri` are invalid for eBPF/syscall rules

## Business Impact

A postgres container has one job — listen on port 5432 and respond to queries. Any shell spawn means a human or process is interacting directly with the container — a reliable signal of either an attacker who has gained pod access, or a misconfigured automation script.

Detecting this at the kernel level (not application level) means an attacker cannot bypass it by modifying application code.
